# Vite+

The `vite` section holds the **entire Vite+ configuration**. Every key is passed
through verbatim to Vite+, so `dbx.config.*` stays the only hand-authored root
config; `dbx sync` writes a thin root `vite.config.ts` that resolves it at load
time.

```ts
export default defineConfig({
    toolchain: {
        vite: {
            fmt: { semi: true, singleQuote: true },
            lint: { ignorePatterns: ['dist/**'] },
            test: { include: ['src/**/*.test.ts'], environment: 'node' },
            run: { tasks: { build: { command: 'tsdown --config-loader unrun' } } },
        },
    },
});
```

The section is typed as Vite+'s own config (`ToolchainViteConfig` = Vite's
`UserConfig` as augmented by Vite+), so the whole Vite+ surface autocompletes in
`dbx.config.ts`.

## The generated shim

`dbx sync` writes a fixed `vite.config.ts`:

```ts
import { defineConfig } from 'vite-plus';

// Generated by @deltabox/toolchain — edit the vite section in dbx.config and run `dbx sync`.
import { resolveVite } from '@deltabox/toolchain/vite';

export default defineConfig(resolveVite({ cwd: import.meta.dirname }));
```

`resolveVite(options?)` resolves the **same-directory** `dbx.config.*` (so a
nested workspace `vite.config.ts` uses its own config), or the `toolchain` you
pass, then returns `toolchain.vite`. The file never drifts, because the real
config stays in `dbx.config.*`.

The root shim must live at the **root**: `vp run`, `vp check` and `vp staged` do
not accept `--config`, so the shim has to be the file Vite+ loads.

## Options

| Option   | Type      | Default | Description                              |
| -------- | --------- | ------- | ---------------------------------------- |
| `config` | `boolean` | `true`  | Write the managed `vite.config.ts` shim. |

Everything else under `vite` is Vite+ config (plugins, `test`, `lint`, `fmt`,
`run.tasks`, ...). Set `vite: { config: false }` to leave a hand-written
`vite.config.ts` alone (the section is still read for provider colouring and the
`dbx` provider passthrough).

## Keep the shim out of Oxfmt

Add `/vite.config.ts` to `vite.fmt.ignorePatterns`, otherwise `vp fmt` rewrites
the generated shim and `dbx sync --check` reports drift:

```ts
vite: {
    fmt: {
        ignorePatterns: ['/vite.config.ts'];
    }
}
```

`dbx migrate --from vite` adds it for you (see
[Migrations](/guide/migrations#vite-config)).

## Commands

Vite+ commands are reachable directly or through the `vite` namespace, and are
registered as a provider (see [Providers](/guide/providers)):

```bash
dbx fmt                 # a bare Vite+ command forwards to `vp fmt`
dbx run -r build        # forwards to `vp run -r build`
dbx vite dev            # explicit namespace (always works)
dbx vite:build          # named alias for `vp build`
```

A bare `dbx <command>` is forwarded to Vite+ when the name (or a Vite+ alias)
matches — built-in commands win, so `dbx migrate` stays the toolchain's
migration.

## Programmatic API

```ts
import {
    resolveVite,
    renderViteConfig,
    viteConfigObject,
    viteProvider,
    viteSyncTask,
} from '@deltabox/toolchain/vite';
```

| Export                      | Description                                                               |
| --------------------------- | ------------------------------------------------------------------------- |
| `resolveVite(options?)`     | Resolve `toolchain.vite` from a `dbx.config.*` (or a passed `toolchain`). |
| `renderViteConfig()`        | The managed `vite.config.ts` shim source.                                 |
| `viteConfigObject(config?)` | The `vite` section without the toolchain opt-out `config`.                |
| `viteSyncTask()`            | The sync task (writes the shim).                                          |
| `viteProvider()`            | The Vite+ provider descriptor.                                            |

See [Configuration](/guide/config#vite) for the `dbx.config` integration and the
[Providers](/guide/providers) guide for the passthrough commands.
