# Migrating from v2 to v3

**v3** is a correctness and cleanup release.

Release notes [here](https://github.com/deltabox-studio/toolchain/releases/tag/v3.0.1).
Full changelog [here](https://github.com/deltabox-studio/toolchain/blob/main/CHANGELOG.md#301-november-2026).

## The most important breaking changes

- The `tsdown` workspace rename to `pack`.
- The redesigned config-generator programmatic API.
- The `dbx()` Vite plugin becoming the preferred config path (available from the `@deltabox/toolchain/vite` subpath as usual).
- Vite+ (`vite-plus`) as the bundled toolchain with per-package releases.
- `fmt`/`lint` moving into `vite.config.*` in Vite+ mode.

## Some of the smaller changes

- Improved changelog and release notes formatting.
- Managed `tsconfig.json` now declaring `include`/`exclude`/`compilerOptions.types` from extended tsconfig.
- UTF-8 BOM support (great for Windows Powershell users).
- Dockerfiles that build from a fresh scaffold.
- Scaffold-only Docker generation.
- `--online` for online templates.
- Stricter nested/configless inheritance and VS Code discovery.
- The `dbx.config.*` format itself is unchanged, so most projects only need to update the dependency and re-run `dbx sync`.
- Idempotent CI releases.

## Breaking changes

### The `tsdown` workspace is now `pack`

The workspace package `@deltabox/toolchain-tsdown` is renamed to
`@deltabox/toolchain-pack`, and the umbrella subpath
`@deltabox/toolchain/tsdown` becomes `@deltabox/toolchain/pack`. The workspace
directory moves from `packages/tsdown` to `packages/pack` and the commitlint
scope changes from `tsdown` to `pack`.

The underlying bundler is still tsdown, so the public helper names
(`baseTsdownConfig`, `createTsdownConfig`, `createPostBanner`) are unchanged. A
consumer only needs to replace the import specifier:

```ts
// v3
import { baseTsdownConfig } from '@deltabox/toolchain/pack';
// v2
import { baseTsdownConfig } from '@deltabox/toolchain/tsdown';
```

Workspace manifests that depended on `@deltabox/toolchain-tsdown` must switch
the dependency name to `@deltabox/toolchain-pack`.

### The `dbx()` Vite plugin is the default config path

New scaffolds are configured through the `dbx()` Vite plugin. Import it from the
`@deltabox/toolchain/vite` subpath: `vite-plugin-dbx` is not published yet, so
the standalone package name is not available to install.

```ts
import { dbx, DBX_TASKS } from '@deltabox/toolchain/vite';
```

The v2 `@deltabox/toolchain-vite` workspace is now `vite-plugin-dbx`, and the
umbrella subpath `@deltabox/toolchain/vite` re-exports it. A managed
`vite.config.*` shim is only written when the project declares its own `vite`
section.

`dbx.config.*` remains fully supported as the non-Vite fallback, so an existing
`dbx.config.*` project does not need to move. If you generate projects
programmatically, expect the generated `vite.config.*` to carry the plugin
instead of a separate `dbx.config.*`.

### Vite+ is the bundled toolchain

**v3** no longer installs `vite`, `vitest` or `tsdown` for you. `vite-plus` is the
single toolchain dependency and provides `vp` (Vite, Vitest, Oxfmt, Oxlint,
Rolldown and tsdown). Replace the individual dev dependencies with `vite-plus`
and use `vp` / `vp run` for those commands.

Workspace packages are released **individually** now: each public `packages/*`
workspace has its own version and `CHANGELOG.md`, and the release workflow
publishes any package whose version is not on npm yet. A consumer that depends on
a published subpackage should track that package's version instead of the
umbrella's.

### Config generator programmatic API

The engine keeps the v2 `createConfigEngine({ schema })` shape, but v3 reshapes
the surrounding API:

- The ambient env declarations are now `dbx-env.d.ts` (previously `env.d.ts`).
  Update the `include`/`files` entries in your tsconfigs if you referenced the
  old file name.
- Runtime loading uses `parseConfig`, `parseEnvConfig` and `parseCliConfig`, plus
  `collect` and `loadConfig` / `loadConfigAsync` for file-backed configs. The old
  `parseEnvTree` + `envString`/`envInt`/`envBool` accessors and `applyOverrides`
  remain available, but are legacy; prefer the parsers so env, CLI and overrides
  are validated through the schema.
- The engine groups its generators: `engine.env` (and `engine.env.types`),
  `engine.types`, `engine.markdown`, `engine.cli`, `engine.jsonSchema` and
  `engine.configJson`. `configCommands({ engine })` now also exposes `config:all`,
  and the standalone `generateConfig*` functions return content unless you pass an
  output path.
- JSON Schema generation can preserve Zod's `$ref`/`$defs` graph
  (`preserveDefs: true`), and the markdown/CLI generators expose more
  frontmatter, scope and reference options. Static schema defaults are also new.

If you only consume the generated files, re-run the generators; if you imported
the engine, update the calls to the grouped API and the runtime parsers.

### Oxc configs live in `vite.config.*` in Vite+ mode

In a Vite+ project, `dbx sync` no longer writes standalone `.oxfmtrc.json` /
`.oxlintrc.json` files. The formatter and linter options live in the Vite config
(`toolchain.vite.fmt` / `toolchain.vite.lint`, or the root `fmt`/`lint`
sections), which Vite+ reads directly.

If an existing Vite+ project has standalone `.oxfmtrc.json` / `.oxlintrc.json`
files, fold them into the Vite config with `dbx migrate --from oxc --write`;
`dbx sync` will no longer write or prune them.

### Project templates are one module per template

The monolithic template module is gone. The supported programmatic surface from
`@deltabox/toolchain/project` (also re-exported by the umbrella) is:

```ts
import {
    createProjectTemplateFiles,
    isProjectTemplateId,
    PROJECT_TEMPLATE_IDS,
    type ProjectTemplateId,
} from '@deltabox/toolchain/project';
```

Look a template up through `PROJECT_TEMPLATE_IDS` / `createProjectTemplateFiles`
instead of importing a shared `qol` helper.

### Docker plans expose their copy sources

`resolveDockerPlan()` now returns `installSources` — the exact files the
Dockerfile copies before installing dependencies. Code that constructs a
`DockerPlan` by hand must provide it; prefer `resolveDockerPlan()` +
`dockerFiles()` instead.

## Behaviour changes

### Config inheritance is strictly opt-in

A nested `dbx.config.*` only inherits the sections it explicitly enables
(`fmt`, `lint`, `biome`, `changelog`, `catalogs`, `logger`); `project` metadata
is inherited except its identity fields. Projects without their own
`dbx.config.*` are unmanaged by default — pass `--configless` or set
`project.manageConfigless: true` to inherit the nearest ancestor config. See
[Nested configs](/guide/config/nested-configs).

### Online templates need `--online`

`dbx create --template <id>` and the `template:*` commands only resolve online
(npm/git/Vite+) sources when `--online` is passed. Local and builtin templates
work without it, and a local-only run never touches the network. Scripts and CI
that relied on implicit online resolution must add the flag.

### Toolchain enable/disable

A top-level `toolchain.enabled` switch is available. The boolean shorthand is
workspace-scoped:

```ts
export default defineConfig({
    plugins: [dbx({ toolchain: { enabled: false } })],
});
```

Config files and the inline `dbx()` plugin only accept the workspace scope; the
object form (`{ disabled, scope: 'global' | 'workspace' }`) is reserved for the
CLI/programmatic API and the VS Code extension. `dbx enable`/`dbx disable` choose
the workspace scope by default; pass `--global` to update
`~/.dbx/toolchain/cli/config.json`. The project config takes precedence over both
the CLI workspace setting and `.vscode/settings.json`.

### Dependabot security updates

`toolchain.ci.dependabot` now accepts an opt-in `security` setting. It adds the
security-update group to `.github/dependabot.yml` and generates
`.github/workflows/dependabot-security.yml` to enable GitHub's native security
updates and optionally dismiss alerts below a severity threshold.

```ts
export default defineConfig({
    toolchain: {
        ci: {
            dependabot: {
                security: {
                    vulnerabilities: { severity: 'high' },
                    pr: { strategy: 'grouped' },
                },
            },
        },
    },
});
```

`security: true` keeps every severity and groups PRs per ecosystem. The workflow
needs a `DBX_GITHUB_TOKEN` secret with repository admin access to change the
repository setting; `GITHUB_TOKEN` is used for alert dismissal. Set
`security: { workflow: false }` to manage the setting yourself, or
`security: { vulnerabilities: false }` to disable security updates. No migration
is required: without `security`, the generated `dependabot.yml` and behaviour
are unchanged.

### Managed-file regeneration

Every managed section now accepts `regenerate?: boolean` (default `true`). Set it
to `false` to skip that section in `dbx sync`: its files are neither written nor
drift-checked, and sync does not prune them. User-owned files
(`tsconfig.workspaces.json`, `tsconfig.build.json`) are only seeded when missing;
an existing file is never overwritten by the missing-file fallback.

### Changelog versioning

- `versioning.target: 'individual'` is idempotent. Commits already listed in a
  workspace's `CHANGELOG.md` are filtered out before deriving its bump, and a
  workspace with no new commits is skipped entirely. Re-running no longer bumps
  untouched workspaces or re-counts an old `feat` as a new minor.
- Workspace glob negation (`['packages/*', '!packages/private-*']`) is honoured.
- A UTF-8 BOM in any `package.json` (common with PowerShell/Notepad) no longer
  makes `dbx changelog` fail; the same BOM handling applies to local CLI
  discovery, providers, Prettier detection and the VS Code extension.
- The `### Package changes` footer now reads Yarn (`.yarnrc.yml`), pnpm
  (`pnpm-workspace.yaml`) and Bun (`package.json` `workspaces.catalog`) catalogs,
  including named catalogs.
- Running changelog from a nested workspace uses the repository root for the
  fallback commit/issue links instead of the workspace's own `package.json`.

### Docker

- Only files that exist when the Dockerfile is generated are copied:
  `package.json` plus the project's lockfile/workspace files. `.node-version*` is
  never assumed, and a missing lockfile is not copied.
- The declared package manager drives both the copy list and the install command.
  A Bun-runtime project with no declared manager installs with Bun; otherwise the
  declared manager wins (so `yarn.lock` is not paired with `bun install`). When a
  Bun-runtime project declares yarn/pnpm/npm, dependencies install in a
  `node:<version>` `deps` stage and the Bun image only builds.
- When there is no lockfile, the install runs without a frozen flag.

### Scaffolding and migrations

- `dbx project:init --out <dir>` (and `project:init:monorepo`) no longer inherits
  the current project's name when `--name` is omitted; it uses the target
  directory's basename. The in-place case still inherits `project.name`.
- `dbx migrate --check` resolves the effective (inherited) config, so a
  workspace inheriting `fmt`/`lint` from the root is not asked to keep an
  intermediate `.oxfmtrc.json` / `.oxlintrc.json`. A disabled section
  (`fmt: false`) does not count as owning the config.

### CLI and VS Code

- `dbx sync --json` always emits a JSON envelope, including when the config
  failed to load (`{ results: [], upToDate: false, error }`).
- `dbx projects --max-depth` rejects non-numeric values instead of silently
  turning the limit into `NaN`; `--max-depth 0` still scans only the root.
- The VS Code extension walks up to the repository boundary for the project's
  `dbx`, checks every workspace root in a multi-root workspace, and keeps the
  project's CLI as the default (the bundled CLI is only the fallback).

### TypeScript declarations

- The shared tsdown base config externalizes declaration imports **as written**
  (`deps.dts.neverBundle: true`), so emitted `.d.ts` files reference bare
  package specifiers instead of build-machine absolute `node_modules` paths.
  Packages whose public types reference another package must declare it in
  `dependencies` (or `peerDependencies`).
- The base config also ships a Rolldown leak reporter. It scans emitted JS,
  declaration and textual asset chunks and fails the build by default when an
  absolute `node_modules` path appears. Configure it via the third
  `createTsdownConfig` argument:
  `{ nodeModulesLeakReporter: { level: 'warn' | 'info' | 'silent', when: 'generateBundle' | 'writeBundle' | 'closeBundle' } }`
  (or `false` to disable it). `writeBundle` is the default; use `closeBundle`
  when a later plugin rewrites output in `writeBundle`. Non-fatal levels respect
  tsdown/rolldown's log level. The plugin is also exported as
  `createNodeModulesLeakReporter` for use in your own builds.

## Recommended upgrade steps

1. Update `@deltabox/toolchain` to v3 and replace the individual `vite`,
   `vitest` and `tsdown` dev dependencies with `vite-plus`.
2. Import the Vite plugin from `@deltabox/toolchain/vite` (not
   `vite-plugin-dbx`, which is not published yet).
3. Run `dbx sync --recursive` and commit the regenerated managed files.
4. Rename generated `env.d.ts` references to `dbx-env.d.ts`, and switch custom
   runtime loaders to `parseConfig` / `parseEnvConfig` / `parseCliConfig` (or
   `loadConfigAsync` for files).
5. Run `dbx sync --recursive --check`, `yarn typecheck`, `yarn lint` and your
   test suite.
6. Regenerate Docker artifacts created by v2 (or edit the `COPY` lines to list
   only files that exist) and rebuild the image once with Docker available.
7. Replace imports of the old monolithic template helper with
   `PROJECT_TEMPLATE_IDS` / `createProjectTemplateFiles`.
8. If you build a `DockerPlan` by hand, add its `installSources` (or switch to
   `resolveDockerPlan()`).
9. Re-run `dbx migrate --check` in CI; inherited workspace configs may now pass
   where v2 reported a false drift.
10. Add `--online` to any `dbx create --template` / `template:*` script that
    resolves npm/git/Vite+ sources.
11. If you use `ci.dependabot`, opt into `security` and add the
    `DBX_GITHUB_TOKEN` secret (repository admin) before the generated security
    workflow runs.
