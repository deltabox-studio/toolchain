# Vite+

The whole Vite+ config lives in `toolchain.vite`. Every key is passed through
verbatim to Vite+, so `dbx.config.*` stays the only hand-authored root config:

```ts [dbx.config.ts]
export default defineConfig({
    toolchain: {
        vite: {
            test: { include: ['src/**/*.test.ts'], environment: 'node' },
            lint: { ignorePatterns: ['dist/**'] },
            fmt: { semi: true, singleQuote: true },
        },
    },
});
```

`dbx sync` writes a thin root `vite.config.ts` that resolves that config at load
time, so the generated file never duplicates (or drifts from) `dbx.config.*`:

```ts [vite.config.ts]
import { defineConfig, type ViteUserConfig } from 'vite-plus';

// Generated by @deltabox/toolchain — edit the vite section in dbx.config and run `dbx sync`.
import { resolveVite } from '@deltabox/toolchain/vite';

export default defineConfig(resolveVite<ViteUserConfig>({ cwd: import.meta.dirname }));
```

The shim imports `defineConfig` from whichever Vite package the project installs
(`vite` or `vite-plus`, detected from `package.json`), so a plain `vite` project
gets `import { defineConfig, type UserConfig } from 'vite'` and
`resolveVite<UserConfig>(...)`.

`resolveVite(options?)` resolves the **same-directory** `dbx.config.*` (so a
nested `vite.config.ts` uses the nested config it sits next to), or the
`toolchain` you pass, then returns `toolchain.vite`. Pass `vite` inline to merge
overrides over the loaded section (`resolveVite({ vite: { ... } })`). It is
exported from `@deltabox/toolchain/vite` for programmatic use too.

The single toolchain opt-out is `config`. Set `vite: { config: false }` to leave
a hand-written `vite.config.ts` alone; set `config` to a string (relative to the
project, or absolute) to write the managed shim at a different path instead.
Everything else under `vite` is Vite+ config (plugins, `test`, `lint`, `fmt`,
`run.tasks`, ...), so `toolchain.vite` is the full Vite+ configuration. The section is typed as Vite+'s own config
(`ToolchainViteConfig` = Vite's `UserConfig` as augmented by Vite+), so the whole
Vite+ surface autocompletes in `dbx.config.ts`.

Add the shim to `vite.fmt.ignorePatterns` so Oxfmt leaves the generated file
alone - without it `vp fmt` would rewrite the shim and `dbx sync --check` would
report drift. In a monorepo put `**/vite.config.ts` on the root config: workspace
`fmt` settings are inherited, but a workspace's `ignorePatterns` array replaces
the root's list. `dbx migrate --from vite` adds it for you.

## Format and lint defaults

Opt in with `vite: { fmt: true }` / `vite: { lint: true }` to use the toolchain
defaults (`DEFAULT_FMT_RULES` / `DEFAULT_LINT_RULES`, exported from
`@deltabox/toolchain`). An options object is merged over those defaults, so
`fmt: { semi: false }` keeps the shared ignores and print width and only changes
`semi`. Shared ignore lists live in `DEFAULT_FMT_IGNORE_PATTERNS` /
`DEFAULT_LINT_IGNORE_PATTERNS`. `sortImports` is never included by default:
import ordering is project-specific, so opt in with your own groups.

## Oxc config files

Vite+ reads `fmt`/`lint` from `vite.config.ts`, but the Oxc VS Code extension
reads `.oxfmtrc.json` / `.oxlintrc.json`. When `vite.fmt` / `vite.lint` are
defined, `dbx sync` writes those files as managed files so the editor picks up
the same configuration. Only the root gets them by default; a nested
`dbx.config.*` gets its own pair only when it defines `vite.fmt` / `vite.lint`
itself (an inherited root config does not create per-workspace files).

To adopt an existing hand-written `vite.config.ts`, fold it in with the
migration (see [Migrations](/guide/migrations#vite-config)):

```sh
dbx migrate --from vite --write   # folds the object into toolchain.vite (+ the fmt ignore)
dbx sync                          # writes the managed vite.config.ts shim
```
